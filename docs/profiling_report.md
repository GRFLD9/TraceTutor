# Отчет по профилированию TraceTutor

## Что профилировалось

Я профилировал основную часть проекта, то есть запуск и трассировку пользовательского кода.

Основная цепочка работы такая:

```text
CodeRunner.run(...)
    -> compile(...)
    -> sys.settrace(...)
    -> exec(...)
    -> ExecutionTracer
    -> TraceResult
```

Также отдельно проверялась новая фича второй итерации - построение timeline выбранной переменной.

## Как запускалось профилирование

Для профилирования использовался встроенный модуль Python `cProfile`.

Скрипт находится здесь:

```text
scripts/profile_tracetutor.py
```

Результат работы `cProfile` сохраняется в файл:

```text
docs/profile_stats.txt
```

Запуск:

```bash
python scripts/profile_tracetutor.py
```

## Какие сценарии использовались

Чтобы профиль был не совсем игрушечным, я использовал несколько более нагруженных учебных примеров:

- много последовательных присваиваний;
- суммирование в цикле;
- частые вызовы функции;
- вложенные вызовы функций;
- рекурсия;
- работа со списком и изменением состояния.

Эти примеры нагружают разные части проекта:

- построчное выполнение;
- обновление локальных переменных;
- циклы;
- вызовы функций;
- возвраты из функций;
- рекурсивный стек вызовов;
- вывод через `print`;
- построение timeline переменной.

## Анализ

### `CodeRunner.run`

`CodeRunner.run` - это главный метод запуска пользовательского кода.

Он делает сразу несколько вещей:

- разбивает исходный код на строки;
- компилирует код через `compile`;
- создает `ExecutionTracer`;
- перенаправляет `stdout` и `stderr`;
- включает трассировку через `sys.settrace`;
- запускает пользовательский код через `exec`;
- ловит ошибки;
- возвращает итоговый `TraceResult`.

Поэтому логично, что `runner.py:33(run)` находится в верхней части профиля. Через этот метод проходит весь запуск.

### `exec`

В профиле также заметен:

```text
{built-in method builtins.exec}
```

Это встроенный механизм Python, который реально выполняет скомпилированный пользовательский код.

В проекте это место выглядит примерно так:

```python
exec(code, namespace, namespace)
```

Именно внутри `exec` выполняются присваивания, циклы, вызовы функций, рекурсия и `print`.

Перед запуском `exec` включается `sys.settrace`, поэтому во время выполнения пользовательского кода Python дополнительно вызывает наш trace-callback. Из-за этого время внутри `exec` включает не только сам пользовательский код, но и работу трассировки.

### `ExecutionTracer`

`ExecutionTracer` получает события от `sys.settrace`.

Основные события:

- `call` - вход в функцию;
- `line` - выполнение строки;
- `return` - возврат из функции;
- `exception` - возникновение исключения.

На этих событиях он собирает `TraceStep`: текущую строку, стек вызовов, локальные переменные, stdout, return value или исключение.

Потенциально дорогие места:

- создание `TraceStep` на каждом шаге;
- сбор стека вызовов;
- сбор локальных переменных;
- вызов `repr` для значений переменных;
- ограничение длины trace.

Для небольших учебных примеров этого хватает с запасом, но на больших программах именно эти части могут стать узким местом.

### `VariableTimelineBuilder.build`

Новая фича второй итерации - timeline переменной - тоже заметна в профиле:

```text
timeline.py:24(build)
```

Это ожидаемо, потому что в profiling-скрипте timeline специально строился много раз.

`VariableTimelineBuilder.build` проходит по шагам `TraceResult`, ищет выбранный frame, затем ищет выбранную переменную и сравнивает ее значение с предыдущим.

Примерная сложность:

```text
O(number_of_steps * number_of_variables_in_frame)
```

Для учебных примеров это нормально, но если trace большой и timeline часто перерисовывается, то эту часть лучше оптимизировать.

## Что можно улучшить

### 1. Кешировать timeline

Сейчас timeline может строиться заново при перерисовке.

Можно сделать кеш вида:

```text
(result_id, frame_depth, function_name, variable_name) -> timeline
```

Тогда при переходе по шагам не придется заново проходить по всему `TraceResult`. UI сможет брать уже готовую шкалу и просто показывать ее часть до текущего шага.

### 2. Ограничить количество переменных

Если во frame много локальных переменных, их сбор и отображение может стать дорогим.

Можно добавить:

- ограничение количества переменных;
- поиск или фильтр по имени;
- скрытие больших объектов;
- отдельный режим раскрытия больших контейнеров.

### 3. Оптимизировать сбор стека

Сейчас стек вызовов снимается на шагах трассировки. Для больших программ можно хранить стек более инкрементально: обновлять его на событиях `call` и `return`, а не пересобирать полностью каждый раз.

### 4. Ленивее обновлять UI

При переходе между шагами сейчас обновляется несколько панелей:

- исходный код;
- таблица переменных;
- стек вызовов;
- explanation;
- timeline.

В будущем можно обновлять только те части интерфейса, которые реально изменились.

### 5. Осторожнее делать `repr`

Для сложных объектов `repr` может быть дорогим или очень длинным. Сейчас длина `repr` уже ограничивается, но можно дополнительно кешировать представления значений или использовать более короткий вывод для больших контейнеров.

## Вывод

Профилирование показало, что для учебных примеров TraceTutor работает достаточно быстро.

Главные затраты связаны с:

- запуском и трассировкой через `CodeRunner.run`;
- выполнением пользовательского кода через `exec`;
- сбором состояния frame;
- построением timeline переменной.

Новая фича `VariableTimelineBuilder` работает корректно, но ее стоит кешировать, если trace станет большим или если timeline будет часто перерисовываться.

Для текущего учебного назначения производительности достаточно. Основные направления будущей оптимизации - кеширование timeline, уменьшение количества пересчитываемых данных и более ленивое обновление интерфейса.
